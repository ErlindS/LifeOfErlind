Interaction With the NvM Module
If your SWC needs to store data nonvolatile, it needs a Nv-block it can interact with. This implicates that typically (-> we will see another approach later) there is a 1:1 mapping between SWC data and NvBlockDescriptors. The Nv-block's characteristics need to be configured in accordance to the requirements of the application data it stores.  
The interaction between the SWC and its assigned Nv-blocks can be done via application callbacks, or more recommendable, via service Client/Server-Ports provided by Rte. Using the C/S-Ports allows to trigger NvM Jobs and get informed about their status. However, the data handover to NvM (in case of a write-Job), or from NvM (in case of a read-Job) per default is done implicitly, while the NvM processes the Job. This leads to the necessity to implement synchronization mechanisms between the Application and the NvM.

**Explicit Synchronization Feature**
One way to make the data synchronization easier is to use the (explicit) Synchronization Mechanism offered in the Nv-block configuration. It will let you define additional Callback functions that will be called, if data is provided or needed by the NvM. The only drawback is, that more user-code needs to be maintained and an additional RAM buffer is generated by the NvM, driving the RAM usage.

Memory Abstraction & Handling
Click on the highlighted buttons below for a short recap on the major topics in the chapters Memory Abstraction and Memory Handling.

1. We always have a RAM-buffer on which the Application is actively working and that needs to be accessed by NvM in case of e.g. Read- or Write-Jobs. These could be triggered using the Rte and C/S-Port connections between SWC and Nv-Block.
2. The RAM-buffer is associated with a Nv-block, whose characteristics can be configured to match the Application-data's needs. E.g.: Very important data might be stored with a CRC and redundantly.
3. If we write this Nv-block to the data flash, then the NvM will call two write commands (one for the primary block, the second for the secondary block). This handling is transparent in the configuration and automatically done, without further interaction of the Application.
4. The MemIf redirects the write-requests to the correct memory technology abstraction. In this example, to the Fee.
5. The Fee abstracts the underlying Flash memory technology and its weaknesses against the NvM with the implemented Partition and Chunk concepts. Chunks hold multiple instances of Fee blocks, which in turn accommodate the Nv-blocks and will be stored in one of the logical sectors specified in Fee's partition.
6. In our example, where we chose to have 3x instances per Chunk and the Nv-block is handled redundant. Consequently, the Fee will instruct the Fls driver to write two independent Chunks to the flash hardware.
7. Another Nv-block might be handled Native and shall be stored in EEPROM memory.
8. Here, the Ea is abstracting the underlying EEPROM memory technology, mitigating its weaknesses with the walking block concept.
9. Depending on the estimated write cycles, the Ea will instruct the Eep to write a number of copies of the Ea block in a round robin manner.
