If you are not familiar with the concept of a finite state machine (FSM), let us clarify it briefly. A finite state machine is a computational abstraction used in computer science, digital logic, and various domains like AUTOSAR, wherein a system can have a limited number of states and can transition between these states based on certain conditions or events. Imagine a simple traffic light system: it can be in one of the states - red, yellow, or green, and it transitions from one state to another based on time or sensor inputs. In the context of AUTOSAR and specifically BswM, FSMs play a crucial role. BswM is responsible for controlling the modes and managing the transitions between these modes based on the overall system behavior and requirements.

With the help of so-called mode declaration groups, defining, managing, and transitioning between different modes of software components is established. Mode declaration groups are essentially a collection of modes where each mode represents a particular state of a software component or module. Think of it like folders in a computer: each folder (mode declaration group) contains different files (modes), and each file corresponds to a specific configuration or behavior of a software module.

Moreover, interactions between different software modules often require synchronization of their modes. With the help of mode declaration groups, BswM can efficiently manage such synchronizations by ensuring that when one module transitions to a particular mode, other dependent modules can adjust their modes accordingly.

# Mode Manager
A **Mode Manager (MMgr)** is any SWC or BSW module which has

- a set of one or more modes (Mode Declaration Groups) which the Mode Manager provides as published information to other SWCs,
- an implementation of the finite state machine corresponding to the published modes and
- the ability to signalize current mode and mode changes over its port interface.

# Mode User
**Mode User (Musr)** is any SWC or BSW Module that 

- requests a mode from a mode manager, e.g. “I am ready for sleep” and / or
- subscribes the mode (switch) information.

Whether a module is manager or user is simply defined with the attached ports prototypes. A module can also be both at the same time.

# **Mode Request**

Receiving a mode request or a mode notification can both initiate a mode change in the mode manager.

To summarize in one sentence: This is done by evaluation of a set of rules with configured triggers and actions contained in action lists in the mode arbitration. But this is a very dense description that requires further explanation of the terms used.

Action: An action can be any function call or a call to an action list.
Action List: An action list contains a list of numbered action items.
Mode Rule: A mode rule is a logical boolean expression which can evaluate to true or false.
Mode Trigger: A mode request or notification that activates the execution of a mode rule.
Mode Arbitration: The process of evaluating mode rules.

The handling of the triggers can be either done in the BswM_MainFunction (deferred) or in an immediate way. Deferred execution of the mode arbitration will therefore poll from a queue during the BswM_MainFunction, where the immediate mode arbitration is executed in the context of the trigger.

# **Mode Notification**
A mode user will receive information about mode switches from the Mode Machine Instance (MMI) generated by the Rte. There are several events available to use for the execution of runnables.
